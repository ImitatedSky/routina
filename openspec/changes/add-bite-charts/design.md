# Design: add-bite-charts

## Context

Bite 目前把資料全部載進記憶體（`BiteRepository` 的 StateFlow），統計是 `data/Queries.kt` 裡的純函式（D1、D9）。
圖表要的東西——區間過濾、每日合計、移動平均——性質完全一樣，所以這一波不需要任何新的資料層，
只要多一組純函式加一個畫面。

兩個約束決定了這份設計的大部分內容：

**約束一：使用者的資料不在「最近」。**
匯入的紀錄是 2025-08-19 到 2025-10-13（31 天），體重 8 筆（2025-07 到 2026-09），而現在是 2026 年 9 月。
「最近 7 天／30 天」對他是空的。任何把預設區間寫死的設計，使用者第一次打開圖表看到的都是空白。

**約束二：視覺規則是硬性的。**
家族累積的視覺研究有幾條已在裝置上驗證的結論，圖表是最容易違反它們的畫面
（圖表天生想要大塊飽和色與粗體數字）：

- **premium colourful is not fewer colours, it is less colour area** —— 顏色面積要小，不是顏色種類要少
- Android ≤14 的 zh-Hant 只宣告 weight 400，`FontWeight.Bold`／`SemiBold` 會被合成假粗。
  **中文層級只能用字級與顏色深淺做**；阿拉伯數字走 Roboto，有真字重，可以 SemiBold
- 中文 `letterSpacing = 0.sp`、行高 1.45–1.5×
- 間距要攜帶分組資訊：組內 < 組間，比例至少 1:2；量表 4／8／12／16／24／32 dp
- 不要三重深度機制（填色＋加深邊框＋靜止陰影），靜止狀態不加陰影
- 不用顏色編碼無意義的維度；類別色上限 8，這裡最多用到 4

## Goals / Non-Goals

**Goals:**
- 回答三個問題：這段時間平均吃多少、體重往哪走、蛋白質夠不夠
- 對使用者真實的資料（不在最近的 31 天）第一次打開就看得到東西
- 完全掌控畫面，逐條符合上面的視覺規則
- 不增加任何相依、不動資料模型

**Non-Goals:**
- 通用圖表元件庫。這三張圖是為這三組資料畫的，不做 `ChartConfig` 之類的抽象
- 縮放、捲動、動畫、浮動 tooltip
- 週／月彙總、自訂區間、匯出圖片（見 proposal 的 Non-goals）

## Decisions

### D1. 自己用 Compose `Canvas` 畫，不用 Vico

**Vico 是實際試過才否決的，不是猜的。** 在這個工具鏈（Kotlin 2.4.10／AGP 9.3.1／Compose BOM 2026.08.00／
compileSdk 37／minSdk 26）上把 `com.patrykandpatrick.vico:compose-m3:3.3.1` 加進 `:apps:bite`，
相依解析成功、`compileDebugKotlin` 綠燈。所以**不是建不起來**。否決的理由有三個：

1. **它把第二套 Compose 相依圖拉進來。** Vico 3.x 是 Compose Multiplatform 函式庫，
   `releaseRuntimeClasspath` 因此多出 20 幾個 `org.jetbrains.compose.*` module
   （runtime、ui、ui-graphics、ui-text、foundation、animation、material3…），
   而 `org.jetbrains.compose.material3:material3:1.9.0` 自己又要求 `androidx.compose.material3:material3:1.4.0`。
   這個專案的 Compose 版本現在由 `libs.versions.toml` 的一個 BOM 決定；加進 Vico 之後
   就多了一個 BOM 管不到的版本來源。專案原則是「長期決策不接受過渡方案」，
   為了三張簡單的圖換掉「Compose 版本只有一個真值」這件事不划算。

2. **視覺規則要求覆寫掉 Vico 幾乎每一個預設值。** 長條要容器色而不是飽和色、
   厚度、無陰影、軸標籤的中文字重與字距、刻度線顏色、格線密度、日期抽稀——
   每一項都要造一個 Vico 詞彙的物件（`Fill`、`LineComponent`、`TextComponent`、`Insets`、
   `ColumnProvider`、`ItemPlacer`、`CartesianValueFormatter`、`ExtraStore`、`MergeMode`）。
   這正是任務描述裡「為了配合它的 API 要寫一堆繞路的程式」那一條。

3. **兩個關鍵行為與它的模型相反。** 其一，選取要的是「圖下方一行文字」，
   Vico 的對應機制是 marker（浮動 tooltip）加 marker visibility listener——我們明確不做浮動 tooltip。
   其二，某區間無資料時要「不要畫一張空的座標軸」，而 `CartesianChartHost` 永遠會把軸畫出來。
   另外資料路徑是非同步的（`CartesianChartModelProducer.runTransaction` 是 suspend 交易），
   在純函式與畫面之間會多一層狀態機，只為了換分頁重算幾十個點。

反過來看自己畫的成本：三張圖都是長條、折線、圓點，資料量上限是「全部」區間的日曆天數
（使用者是 56 天，十年後也才三千多個點，而畫面只有幾百 px 寬），
不需要虛擬化、不需要捲動。`Canvas` + `TextMeasurer` 大約三百行就結束，配色與字體完全可控，
零相依風險。

**代價（誠實記下）**：軸刻度、日期抽稀、命中測試這些是自己寫的，沒有函式庫的測試覆蓋；
之後要加捲動或動畫就得自己補。這一波不需要它們。

### D2. 沒有紀錄的日子不補 0，x 軸走真實日曆天

兩個都不誠實的做法先排除：

- **補 0**：畫出一根貼地的長條，讀起來是「那天沒吃東西」。更糟的是它汙染統計——
  平均被拉低、最低值永遠是 0、移動平均在斷點塌陷、達標天數把沒記錄的日子算成達標。
- **只排有紀錄的日子（index 軸）**：把 2025-09-20 到 2025-10-01 的空窗壓成零寬度，時間比例是假的。

所以：**x 軸是區間第一天到最後一天的真實日曆軸（等時距），沒有紀錄的日子就是沒有長條**。
空白本身就是「那天沒記」的訊息，而且它不參與任何統計。所有摘要（平均、最高、最低、達標率）
的分母一律是**有紀錄的天數**，畫面上也照這樣講（「達標 18／23 天」）。

體重折線例外：兩筆量測之間連線。體重是連續量，中間那條線是內插而不是捏造資料，
而且每一筆量測本身有點標記，讀者看得出來哪裡是實測。

### D3. 區間：7／30／90／全部，預設 30 天，空區間自動退回「全部」

`Range` 是四個值的 enum。進畫面時算一次：若「最近 30 天」內既沒有飲食紀錄也沒有體重紀錄，
就改用 `ALL`，並在區間列下方留一行說明（「最近 30 天沒有紀錄，顯示全部」）。

- **區間是三個分頁共用的**，不是每個分頁一份。切分頁時區間跟著走，不會偷偷改掉。
- **退回只在開畫面時判斷一次**。使用者手動選了一個空區間，就照他選的顯示空狀態——
  他自己按的，不需要 App 幫他改。
- 判斷依據是「飲食或體重任一有資料」而不是分頁各自判斷，否則切分頁會看到區間自己跳掉。

`ALL` 的範圍＝**該張圖自己的資料**的最早到最晚日期（不是到今天）。使用者的資料在一年前，
畫到今天會多出十個月的空白；而飲食紀錄止於 2025-10-13、體重量到 2026-09，
用「兩者聯集」當範圍會讓熱量圖右邊拖出十一個月的空白。區間的**選擇**是共用的，
每張圖再各自算自己的起訖。

### D4. 三種顏色角色，飽和色只給細線

長條是整張圖裡面積最大的東西，所以它必須是最低飽和的：

| 角色 | 顏色 | 形態 | 面積 |
|---|---|---|---|
| 資料長條（靜止） | `surfaceVariant` | 實心圓角 | 大 |
| 資料長條（選取中） | `onSurfaceVariant` | 實心圓角 | 一次一根 |
| 7 日移動平均 | `primary` | 2dp 實線 | 細線 |
| 目標線 | `outline` | 1dp 虛線＋數值標籤 | 細線 |
| 格線／軸 | `outlineVariant` | 1dp | 細線 |
| 折線圖的選取指示 | `onSurfaceVariant` | 1dp 垂直參考線 | 細線 |

選取態**不用顏色，用同色系的深淺**（`surfaceVariant` → `onSurfaceVariant`），
這是研究裡「層級用深淺做」那一條，也避免「同一個顏色同時意味目標與選取」。
選取的長條不加邊框、不加陰影——**單一深度機制**。
折線圖沒有長條可以加深，所以改畫一條中性色的垂直參考線；兩種都是中性色，都不是「又一個類別」。

三大營養素沿用既有的 `MacroColors`（蛋白質 #4E8A7B／脂肪 #C2895A／碳水 #8A7BB5），
只畫在折線與 12dp 圖例色塊上。體脂折線用 `MacroColors.Fat`——體脂對應脂肪，
是既有語意的延伸，不是新色系。

全畫面類別色合計 4 種（primary＋三個 macro），在 8 種上限內。

### D5. 文字：中文靠字級與深淺，數字才用 SemiBold

- 圖表內的軸標籤、圖例：`labelSmall`／`onSurfaceVariant`，一律 weight 400
- 摘要卡的標題（中文）：`bodyMedium`／`onSurfaceVariant`，**不加字重**
- 摘要卡的數值：`titleMedium` + `FontWeight.SemiBold`——Roboto 有真字重，
  這是 App 現在唯一一處 SemiBold 的用法，照著延續。
  **單位寫進中文標題裡**（「平均（大卡）」），數值那一格只留數字，
  這樣 SemiBold 不會壓到任何中文字
- 分頁標題、選取態文字列：中文，維持 `bodyLarge`／`bodyMedium`，靠顏色深淺分層
- 中文區塊一律 `letterSpacing = 0.sp`

### D6. 間距：組內 8dp，組間 24dp

畫面由上到下是「區間列 → 圖 → 選取態 → 摘要卡」四組。

- 組內（摘要卡裡一格的標題與數值、圖例項目之間）：**4dp / 8dp**
- 組間（區間列與圖之間、圖與摘要之間）：**24dp**
- 卡片內距：水平 16dp、垂直 12dp；圓角 12dp（沿用家族值）
- 比例至少 1:2，符合「間距要攜帶分組資訊」

### D7. 營養素分頁用 small multiples，不用堆疊長條

三條小型折線（各一張小圖，共用 x 軸的日期抽稀），不是堆疊長條。理由：

1. **堆疊圖的中間段讀不出來。** 脂肪那一段的基線隨蛋白質浮動，人眼無法比較它跨日的高度。
   而使用者的問題正好是「脂肪有沒有變多」。只有最底下那一段是可讀的。
2. **堆疊長條要三個飽和色鋪滿整張圖。** 這是 D4 的正面衝突：三條細折線的著色面積不到它的 5%。
3. **三個數字堆起來的總高度沒有意義。** 1g 脂肪是 9 kcal，蛋白質與碳水是 4 kcal，
   公克數的和不是任何東西。
4. **各自的目標線可以分開畫。** 蛋白質一定有目標，脂肪與碳水可能沒有（`Targets` 裡是 nullable）；
   small multiples 讓「有目標的畫線、沒目標的不畫」變成三次獨立判斷，而不是一張圖裡的例外。

代價：看不出單日的組成比例。那是今日頁三條進度條已經回答的問題，而且是單日問題不是趨勢問題。

### D8. 體重的兩種來源用點的形狀區分，不用顏色

家用體重計＝實心圓（4dp 半徑，`primary`），InBody＝空心圓（`primary` 描邊 1.5dp、`surface` 填）。
用形狀不用顏色的理由：來源是資料的後設屬性，不是另一個資料系列；
給它一個顏色會讓畫面上的類別色從 4 個變 5 個，而且色盲條件下讀不出來。形狀在兩種條件下都成立。
圖例放在圖的正下方（組內 8dp），兩個小圖示各配一行中文。

體脂折線疊在同一張圖上（不是第二張小圖），用**右側第二個 y 軸刻度**。同一張圖的理由是
體重與體脂是同一件事的兩面，使用者要看的是「體重降的時候體脂有沒有跟著降」——
拆成兩張圖就要用眼睛在兩張圖之間對齊 x 軸。虛線＋不同色＋右軸三個線索一起用，不會誤讀成體重。
沒有任何一筆有體脂率時整條線與右軸都不畫。

### D9. y 軸刻度取「好數字」，x 軸日期依可用寬度抽稀

- y 軸：以 4 段為目標算間隔，取 1／2／5 × 10ⁿ；向外對齊到整數刻度後若超過 5 段，
  就換大一級的間隔重算，所以刻度最多 6 條。
  熱量與營養素的 y 軸從 0 起；**體重不從 0 起**，範圍取 `[min - padding, max + padding]`
  再對齊到刻度間隔，最低與最高刻度都標出來，讀者一眼看得到範圍。
- x 軸：一個 `M/d` 標籤約需 40dp，`step = ceil(天數 / (寬度 / 40dp))`，只畫 `index % step == 0` 的。
  這樣 7 天畫 7 個、56 天畫 7 個左右，**永遠不疊字**。

### D10. 選取：點按換算回日期，顯示成圖下方一行文字

`Modifier.pointerInput` + `detectTapGestures`：把 tap 的 x 換算回日曆 index，
取那天（沒有紀錄就取最近的有紀錄的那天，容差 1 天）。選中的日子存在畫面的 `remember` 狀態裡，
圖重畫時把那一根長條／那個點加深。下方固定高度一行文字顯示「10月13日：2193 大卡」，
沒有選取時顯示提示（「點圖上的資料看單日數值」）。這一列有最小高度，沒選取時版面不會塌下去；
營養素分頁的文字較長，允許折行而不是截斷。

換區間或換分頁時清掉選取（那個日期在新的區間裡可能不存在）。

### D11. 檔案切分

| 檔 | 內容 | 為什麼分開 |
|---|---|---|
| `data/Trends.kt` | 區間過濾、每日合計、移動平均、極值、達標天數，全純函式 | 與 `Queries.kt` 同一個角色。**放新檔而不是加進 `Queries.kt`，是為了與平行進行的食物分類 change 不衝突** |
| `ui/Charts.kt` | Canvas 繪圖基礎：座標換算、y 軸刻度、x 軸抽稀、長條、折線、點、選取命中測試 | 三個分頁共用，而且是唯一碰 Canvas 的地方 |
| `ui/ChartsScreen.kt` | 畫面骨架、TabRow、區間列、三個分頁內容與摘要卡 | UI 組裝 |

`Trends.kt` 的輸入是 `List<DiaryEntry>`／`List<WeightEntry>`／`Targets`，輸出是畫圖用的 data class；
不碰 Compose、不碰 repository。

### D12. 路由 `charts?tab=`，兩個入口

`charts?tab={tab}`，`tab` 是選用字串參數，`defaultValue = "kcal"`，值是 `kcal`／`weight`／`macros`。
歷史頁的圖示開 `charts`（落在熱量），體重頁的圖示開 `charts?tab=weight`。

**今日頁不放入口。** 今日頁是「記錄」的地方，它的 TopAppBar 已經有三個圖示（歷史、體重、設定），
再加一個會讓最常用的那一頁變成工具列。趨勢屬於「回顧」，掛在既有的兩個回顧頁是對的位置，
而且從體重頁進去直接落在體重分頁，比從今日頁進去再切分頁少一步。

## Risks / Trade-offs

- [自己畫的軸刻度與抽稀沒有函式庫的測試覆蓋，極端資料（單日、全部同值、極大值）可能出怪版面]
  → `niceStep` 對 `max == min` 與 `max == 0` 有明確分支；單點的折線畫成一個點不畫線。
- [**完全沒有實機或 Preview 算圖驗證**，只有 debug／release 編譯綠燈與把軸刻度、日期抽稀、
  移動平均三段邏輯照抄成腳本跑過對照] → 所有尺寸用 dp 換 px、不寫死 px，字體走 MaterialTheme
  typography 不自訂 sp；但版面是否真的好看、標籤會不會在低密度螢幕上擠在一起，要合併後在裝置上看。
- [`ALL` 區間十年後有三千多個日曆天] → 長條寬度會小於 1px。這一波不處理；
  真的變成問題時的解法是週彙總（已列在 Non-goals），不是捲動。
- [移動平均在紀錄稀疏的區段會誤導] → 以當天為右端的 7 個日曆天內，**有紀錄的日子至少 4 天**才畫點，
  不足就斷開。線斷開比畫一條由兩筆資料撐起來的「週平均」誠實。
- [體脂與體重疊在一張圖可能被誤讀成兩條體重線] → 體脂是虛線、不同色、走右側刻度，三個線索；
  圖例寫明單位。
- [與平行進行的食物分類 change 在 `MainActivity.kt`、`strings.xml` 會衝突]
  → 兩邊都只加自己的東西：route 加在 NavHost 尾端、字串附加在 `strings.xml` 檔尾。
  `Queries.kt`、`TodayScreen.kt`、model、repository 完全不碰。版號不動。

## Migration Plan

沒有資料要遷移，沒有格式變更。這個 change 只讀既有的 StateFlow。
舊版 App 的資料檔在新版可以直接用，反之亦然。

## Open Questions

- 移動平均的「至少 4 天」與 x 軸標籤的 40dp 都是憑手感定的常數，等實機看過再調。
- `ALL` 區間畫到最後一筆紀錄而不是今天，代表「我已經兩週沒記了」這件事在圖上看不出來。
  目前認為那是歷史頁的工作，不是趨勢圖的。
